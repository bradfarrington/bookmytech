**⚠️ THIS REPO IS NOW ALSO A MOBILE BACKEND. Read `AGENTS.md` → "A customer mobile app consumes this codebase" before changing anything.** A customer mobile app (React Native / Expo) lives in a separate repo, `bmt-customer-app`, and shares this database, this business logic and these integrations. It reaches us through HTTP route handlers under `app/api/mobile/v1/` (Bearer tokens, JSON, no cookies, no redirects) and by reading Supabase directly under the existing customer RLS policies.

The consequence that changes how you work here: **a mobile app cannot be force-updated.** Old builds stay on people's phones for months and keep calling whatever they shipped with. So a shipped API path, response shape or field name is a **contract** — additive changes are safe, renames and removals are not. Ask "would a phone running last month's build still work after this?", and **say so explicitly in your summary to Brad whenever a change needs work in the app repo** — every schema migration does, because the app generates its types from the live schema. The full standing rules and the list of always-report changes are in `AGENTS.md`; the architecture split is in `docs/01-architecture.md`.

**Web checkout: missing Stripe `return_url` ✅ (2026-08-05).** Found by Stripe's own monitoring, not by us — confirmations were being **rejected outright** whenever the issuer wanted a 3-D Secure challenge it wouldn't run in Stripe's iframe. The customer saw "Payment failed. Please try again." and retrying never helped, because it failed identically every time for the same card. It survived testing because the common test cards authorise without a challenge. **The mobile app was never affected** — `StripeProvider` there supplies `urlScheme="bmtcustomer"`, which is how stripe-react-native builds its return URL. Detail in [docs/tasks/03-booking-flow.md](tasks/03-booking-flow.md).
- **`redirect: "if_required"` does not make `return_url` optional.** It means "don't redirect unless you have to"; when Stripe decides it does have to and finds no return URL, it refuses the confirmation. Nothing is held, so no booking row is written — the funnel just dead-ends.
- `prepareCheckoutFor` now pins the intent to `payment_method_types: ["card"]`. Left unset it offered whatever the Stripe dashboard had enabled, including redirect-only methods that have no business on a manual-capture hold captured days later. **This is shared with the mobile app's PaymentSheet** (same `prepareCheckoutFor`), which now offers card only — no app-side change needed, but it changes what the sheet shows.
- **The return path is the substance of the fix, not the `return_url` line.** A redirect that fires unmounts `SlotPicker` and destroys every answer the customer gave (slot, address, parking, instructions, name, email, and the `checkout` result) while the hold goes live on their card — landing them on an empty "Pick a time" form, charged, with nothing in the CRM. Strictly worse than an honest error. So the draft is parked in `sessionStorage` keyed by PaymentIntent id **before** confirming, and replayed on return: retrieve the intent, and on **`requires_capture`** write the booking and go to `/book/confirmed/[id]` exactly as the non-redirect path does.
- **`requires_capture`, not `succeeded`.** A confirmed manual-capture hold never reaches `succeeded` until the job is captured — testing for `succeeded` would reject every good payment. Statuses that hold nothing (`requires_payment_method` and friends) restore the draft onto the form and show the error instead of resetting the customer to step one.
- Ordering is unchanged: hold first, then write the row, so "a payment failure leaves no orphaned booking row" still holds. The new case is the **other** direction — a live hold with no booking — which is now reported: `app/actions/orphaned-hold.ts` re-reads the intent's status from Stripe, skips it if a booking row already exists, then logs, records an `orphaned_hold` funnel event and emails `ADMIN_ALERT_EMAIL`. **It is a public endpoint, so it needs two spam gates, not one:** re-reading from Stripe kills fabricated intent ids, but a *genuine* orphan passes every check on every call by definition, so it also **alerts at most once per intent id** — the `orphaned_hold` event doubles as the record of having alerted (`funnel_events.event_name` is free-form, so no migration). Caught in review by the app repo. The customer is told plainly that funds are held and to contact us. The hold releases itself after 7 days.

**Mechanic balance ledger + admin refund clawback ✅ (2026-07-01).** Migration `0034`. A new money-recovery layer on top of the instant-payout model.
- **Model (owner decision 2026-07-01):** mechanics are still paid **instantly** on job completion — BMT does **not** hold their money or run scheduled payouts. But when an admin refunds a customer, BMT fronts that cash from its **own Stripe balance**, and the mechanic (already paid) is put into **debt**: their balance goes **negative** and is **netted off their next job's payout** before any transfer goes out. Only the surplus transfers; the withheld part repays what BMT fronted.
- **Schema (`0034`):** `mechanic_ledger` — append-only signed-pence ledger (`earning` +, `payout` −, `refund_clawback` −, `adjustment` ±). `balance = SUM(amount_pence)` = what BMT owes the mechanic (negative = they owe BMT). Sits at ~£0 in steady state (earn then instantly pay out); only goes negative between a refund and its recovery. RLS mirrors `customer_credits`: mechanic reads own, admin reads all, **service-role writes only** (no browser INSERT).
- **Helpers** ([lib/mechanics/balance.ts](../lib/mechanics/balance.ts)): `mechanicBalancePence`, `mechanicBalanceSummary`, `recordEarning`/`recordPayout`/`recordRefundClawback`. Pure netting maths `nettedPayout(priorBalance, gross)` lives in [lib/earnings.ts](../lib/earnings.ts) (**8 new unit tests**, `npm test` now 47).
- **completeAndCharge** ([job-progress.ts](../app/actions/job-progress.ts)) now: reads prior balance → records the gross `earning` → transfers only `nettedPayout(...).transferPence` (not the full payout) → records the `payout` row → logs a `note` event for any amount withheld to recover a debt. A failed transfer writes no payout row, so the balance stays positive (owed) for retry — more correct than before.
- **Admin refund** ([bookings.ts](../app/actions/bookings.ts) → `refundBooking(bookingId, amountPence, reason)`): admin picks the amount (clamped to charged − already-refunded), refunds the card via `refundPayment`, writes a `payment_refunded` event, then `recordRefundClawback` debits the assigned mechanic (no mechanic → BMT absorbs it). UI is a **Refund customer** panel in the job-detail actions ([booking-actions.tsx](../app/(admin)/admin/(shell)/jobs/[id]/_components/booking-actions.tsx)); the Payment card shows the already-refunded total.

## Working principles

- **Read before writing.** When asked to do a task, first summarise back what you understand and the steps you'll take. Don't write code until the human has confirmed.
- **Server components by default.** Add `"use client"` only when interactivity is needed.
- **Tailwind v4 utilities only.** Tokens live in `@theme` in `app/globals.css` and are referenced by name (`bg-brand-blue`, never `bg-[#2563EB]`). There is NO `tailwind.config.ts` — v4 is CSS-first.
- **Money is integer pence.** Never floats.
- **Update this HANDOFF when a task completes.** Mark what changed, what's the new "current task".

## Stack quirks worth knowing

- **Next 16** has deprecated `middleware.ts` in favour of `proxy.ts`. Renaming + updating the export name is a tiny follow-up but harmless to defer.
- **Tailwind v4** uses CSS-first config via `@theme { ... }` in `app/globals.css`. No `tailwind.config.ts` file.
- **`lucide-react` v1** dropped brand icons (Twitter/Instagram/LinkedIn). Hand-rolled SVGs live inline in `app/(customer)/_components/footer.tsx`.
- **`Icon` primitive** takes an `icon: LucideIcon` component prop, not a `name` string — preserves tree-shaking. Call sites: `import { Zap } from "lucide-react"; <Icon icon={Zap} />`.
- **Route groups + `tsc`**: bare `npx tsc --noEmit` reports a false-positive validator error because `.next/types/validator.ts` doesn't perfectly track route groups (looks for `app/page.tsx` when the page is at `app/(customer)/page.tsx`). `npm run build` passes cleanly — the build pipeline handles route groups correctly.
- **DVLA vs DVSA**: DVLA Vehicle Enquiry Service gives tax/MOT status but **not** the model. DVSA MOT History API gives the model (and full MOT history). We hit both in parallel and merge — see `app/actions/lookup-vehicle.ts`. Required env vars when running with real keys: `DVLA_API_KEY` (VES) plus `MOT_API_KEY` / `MOT_CLIENT_ID` / `MOT_CLIENT_SECRET` / `MOT_TOKEN_URL` / `MOT_SCOPE` (MOT). Missing either set falls back gracefully — DVLA to stub data, MOT to "no model".
